## 2. 实验一：边缘-中心架构可扩展性实测

### 2.1 两种架构的严格定义

| | 方案 α · 集中式 | 方案 β · 分布式（本系统） |
|---|---|---|
| 节点职责 | 只采集：摄像头取帧 → H.264 编码 → RTSP 推流到 PC | 本地 NPU 推理 → 只把结构化元数据用 UDP 发 PC |
| PC 职责 | 解**N** 路流 + 跑**全部**推理 | 收元数据 + 融合 + 看板 + 日志 |
| 上行数据 | N 路 1080p 视频流 | N 路约 **55–75 B/s** 的 JSON（单节点：`@E` 2 s/帧、≈45 B/帧；4 节点 220–300 B/s） |
| 断网行为 | 全部失效（视频到不了 PC） | 节点仍本地报警（SIL-1 由 Arduino 保证） |

### 2.2 公平性约束（必须先写进报告，不能事后补）

1. **同一算法、同一模型**：α 与 β 都用同一个检测模型；α 在 PC 上跑，β 在节点 NPU 上跑，二者的输入分辨率必须相同（都取 768×432）。
2. **同一硬件**：α 与 β 用同一块 PC、同一块网卡、同一台路由器；节点不换。
3. **同一场景**：两种方案在**同一次走位**上采集（同一人按同样路线走，或同一段录像回灌），避免场景差异污染结论。
4. **β 的推理开销不能藏**：节点侧 NPU 占用与功耗要单独记录，否则"边缘更省"会被质疑为"把开销藏到看不到的地方"。**α 的 PC 侧没有对应开销，这是 β 的真实成本，必须明说。**

> ⚠️ 若 α 在 PC 上跑不动 N 路（很可能），**这不是失败，是结论**。正确做法是记录"α 最多能实时处理几路（N_max）"，并把 N_max 作为中心瓶颈的量化证据。

### 2.3 自变量

| 维度 | 取值 | 说明 |
|---|---|---|
| 架构 | α / β | 见 §2.1 |
| 节点数 N | **1, 2**（现有硬件）；补到 4 套后加 **4** | N=3 需要 3 块板，现有硬件做不到；**不要用合成流量伪造 N=3**，若确实需要，必须标注为"模型推算值"并与实测点分开画 |

### 2.4 因变量与测量口径（★ 定死再测）

| # | 指标 | 严格定义 | 采集工具 | 精度/局限 |
|---|---|---|---|---|
| 1 | **上行带宽** | 测量窗口内各节点网卡 `tx_bytes` 增量之和 ÷ **`duration_s`（实测时长，不固定除 60）**，单位 B/s（报告可换 KB/s） | 节点侧 `cat /proc/net/dev` 由脚本每 5 s 采样，PC 侧 `iftop` 交叉验证 | `tx_bytes` 含协议头与重传，比"有效载荷"偏大，**报告里要说明这是链路层口径** |
| 2 | **PC 端 CPU 占用** | 稳定运行 60 s 的平均值（%），重复 3 次取中位数 | Windows 性能监视器 / Python `psutil` | 单核百分比还是全核百分比要写清；建议用"进程 CPU 时间 ÷ 墙钟时间 ÷ 核数" |
| 3 | **端到端响应时间** | 从"人进入画面"到"看板出现该事件" | 手机录像 → 逐帧回放计数 | 误差 = `±(1000/node_fps + 1000/rec_fps/2)`，**每 run 逐次算**（节点 30 fps + 录像 60 fps ≈ ±42 ms；录像 30 fps ≈ ±50 ms）；**不写固定值**，`node_fps`/`rec_fps` 当场实测；人工计数**必须由同一人完成全部测量** |
| 4 | **丢包率** | `(最大 seq − 实际收到条数) ÷ 最大 seq` | PC 侧 `metrics` 模块按 `seq` 统计 | 只在 β 有意义（α 走 RTSP/TCP，丢包表现为花屏而非丢帧） |
| 5 | **断网可用性** | 定性：拔网线后 10 s 内，本地蜂鸣器/继电器是否按预期动作 | 手工操作 + 录像留证 | 二值结论，附录像时间点 |
| 6 | **节点侧开销**（β 专属） | NPU/CPU 占用（`top`）、单节点功耗（USB 电流表 × 5V） | 节点侧 `top`、USB 电流表 | 无电流表时此项标"未测"，**不要估算** |

### 2.5 测量流程（每次取数照此执行）

```
1. 预热 5 分钟（避免冷启动抖动）
2. 清空日志，记录起始时间与 N、架构
3. 场景：一人从 A 区走到 B 区，走 3 趟（约 30 s/趟）
4. 持续 60 秒，期间不做其他操作（不下载、不看视频）
5. 停止，导出：节点 /proc/net/dev 采样、PC 进程 CPU、看板事件时间戳、录像
6. 换下一个 (架构, N) 组合，重复
7. 每个组合至少 3 次，取中位数；离散度写进报告
```

**顺序建议**：先 β(N=1) → β(N=2) → α(N=1) → α(N=2)。先做 β 是因为它是主方案，越早拿到数据越能发现问题。

### 2.6 记录表（每次实验填一行，可直接复制到报告）

| 日期时间 | 架构 | N | 上行带宽 KB/s | PC CPU % | 端到端 ms | 丢包率 % | 断网可用 | 节点 NPU % | 备注 |
|---|---|---|---|---|---|---|---|---|---|
| | α | 1 | | | | — | | — | |
| | α | 2 | | | | — | | — | |
| | β | 1 | | | | | | | |
| | β | 2 | | | | | | | |

> **原始数据不删**：`metrics` 模块把每条报文按 JSONL 落盘，实验后打包进交付物。报告里的均值必须能通过这些原始文件复算出来。

### 2.7 预期结论与写法

预期（**先写预测，再用数据检验，这是科学报告的基本姿态**）：

- 带宽：α 随 N **线性增长**；β 几乎**恒定**（每节点仅几百 B/s）→ 两条线**分叉**
- CPU：α 在 N 增大时迅速饱和甚至掉帧；β 始终轻载
- 可用性：α 断网即全面失效；β 断网后节点仍本地报警

**结论的正确写法**（示例，等实测后替换）：

> 在 N=1→2 的过程中，α 方案上行带宽由 __ KB/s 增至 __ KB/s（约 __ 倍，接近线性），β 方案由 __ B/s 变为 __ B/s（基本不变）；PC 侧 CPU 占用 α 从 __% 升至 __%，β 维持在 __%。受硬件限制本次只测得 N=1,2 两点，已能看出斜率差异；N=4 的分叉拐点作为后续工作。

**不要写**："边缘计算明显更优"——这句话没有信息量，也没有数据支撑。

## 3. 实验二：视觉计数准确率标定

### 3.1 为什么做这个实验

视觉系统报"这小时进了 12 个人"，凭什么信？**由 U 型光电传感器提供独立于视觉的人次真值**，把"演示"变成"测量"。这是套件（51 项）给本项目带来的最大增量。

### 3.2 真值与被测

| 角色 | 来源 | 说明 |
|---|---|---|
| **真值** | U 型光电传感器（遮挡即 1 人次） | 与视觉完全独立的物理通道；响应快（μs 级），不受光照影响 |
| **被测** | Duo 视觉人次计数 | 同一场景同一时段，两边各自计数 |

> ⚠️ 光电只能测"有人通过"，不能分辨"是谁"。它给的是**通过人次真值**，不是身份真值——结论限定在计数维度。
>
> **真值口径唯一（v1.1c）**：本实验真值**只认 U 型光电**（`@C` 累计人次）。某组光电不可用时**整组**改"人工计数 + 录像回放"，`note` 写 `#manual_truth`；**同组不得混用两种真值**，混用的组整组作废。这句话与 `11 §五`、契约 3 §3.1 逐字一致，改一处必改三处。

### 3.3 自变量（3 × 2 × 2 = 12 组条件）

| 维度 | 水平 | 说明 |
|---|---|---|
| 光照 | 正常开灯 / 关灯（仅走廊光）/ 侧逆光（窗光直射镜头） | 逆光是最容易崩的条件 |
| 通过速度 | 正常步行（约 1.2 m/s）/ 快走（约 1.8 m/s） | 速度影响帧间位移，进而影响跟踪连续性 |
| 朝向 | 正面（面向镜头）/ 侧身（侧面通过） | 侧身时人脸检测置信度下降 |

### 3.4 样本量与执行

- **每种条件 10 人次**，共 120 人次；条件顺序打乱，避免疲劳/光线渐变造成的系统偏差
- 由**同一个人**完成全部通过动作（控制变量）；若换人，换人点必须记录
- 每次通过间隔 ≥3 s，确保光电与视觉都"闭合"了一次
- 全程录像留证，**记录每一个漏检/误检的具体时刻**，便于回放定位

### 3.5 指标定义

| 指标 | 定义 |
|---|---|
| 漏检率 | 光电计数 > 视觉计数的差额 ÷ 光电计数 |
| 误检率 | 视觉计数 > 光电计数的差额 ÷ 光电计数 |
| 计数偏差 | (视觉计数 − 光电计数) ÷ 光电计数 |
| 置信度分布 | 检测框置信度 `s` 的分布（低置信度多 → 说明条件恶劣） |

### 3.7 预期结论与写法

预期：正常光照 + 步行 + 正面时准确率最高；**逆光**与**快走**是主要失效条件。产出一张"不同条件下视觉计数准确率"热力表 + 一条工程结论，例如：

> 在本实验的 12 组条件中，视觉人次计数在正常光照步行条件下偏差为 __%，在侧逆光快走条件下偏差达 __%。因此本系统在门口场景应固定补光、并把计数口径限定为步行速度；对快走场景需降低置信度阈值并接受更高误检。

## 4. 实验三：防尾随检测的误报/漏报率

**判定逻辑**：一次合法通行 = 刷卡(UID) + 光电计数 1 人次 + 视觉 1 人（且方向一致）。若光电计到 2 人次而刷卡仅 1 次 → 疑似尾随。

| 场景 | 期望 | 实际 | 判定 |
|---|---|---|---|
| 1 人刷卡正常通过 | 无告警 | | |
| 2 人贴身通过，只刷 1 次卡 | 尾随告警 | | |
| 1 人刷卡后倒退再进 | 无告警（同一人） | | |
| 2 人先后间隔 2 s 各刷 1 次 | 无告警 | | |
| 1 人刷卡，另一人从侧面绕过门磁 | 漏检（记录为已知局限） | | |

每组做 10 次，记录误报率与漏报率。**侧绕是这套方案的固有盲区，报告里要主动承认**——承认盲区比假装没有盲区更能加分。

## 6. 风险与降级

| 风险 | 影响 | 降级方案 |
|---|---|---|
| α 在 PC 上跑不动 2 路 | 没有 α 的 N=2 数据点 | 记录 N_max（能实时处理的最高路数），把"只能撑 1 路"当结论；β 数据点照常 |
| 只有 2 套板，N 只能到 2 | 曲线只有两点，看不出拐点 | 补 2 套（见 05 §3）；或明确标注"两点测斜率，拐点为后续工作" |
| 端到端延迟人工计数误差大 | 数字被质疑 | 写明 ±1 帧精度与操作者；或用"PC 收到时间 − 节点打点时间"作为补充口径 |
| 没有 USB 电流表 | 功耗一项空着 | 标"未测"，**不要估算** |
| 光电真值本身有误差（连走两人） | 实验二真值不准 | 通过间隔 ≥3 s；连续通过单独记为"合并事件"并在报告中说明 |
