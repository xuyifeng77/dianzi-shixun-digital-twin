## 2 固件缺陷（按严重度）

### 🔴 高-1｜DS18B20 采样阻塞约 750 ms（`sampleSensors()` 第 125 行）

`ds18.getTempCByIndex(0)` 是**同步等待转换完成**的调用（12 位分辨率约 750 ms）。后果：
- 固件"全程非阻塞"的说法不成立，主循环每秒卡 750 ms；
- 卡住期间 `handleSerial()` 不执行，48 字节缓冲可能溢出丢帧；
- 报警响应最长推迟 750 ms（仍 <3 s 指标，但违背设计）。

**最小修复（二选一）**
```cpp
// 方案A（推荐，改 2 行）：降分辨率到 9 位，转换仅 94 ms
//   setup() 中：
ds18.setResolution(9);
// 方案B：两段式非阻塞
//   setup(): ds18.setWaitForConversion(false);
//   sampleSensors(): ds18.requestTemperatures();      // 只发请求
//   下一拍(1s 后)再 getTempCByIndex(0) 读缓存
```

### 🔴 高-2｜门磁极性与上拉自相矛盾（第 255–262、310 行）

代码 `pinMode(PIN_DOOR, INPUT_PULLUP)` 却判定 `closed = (digitalRead == HIGH)`。
- 若干簧管直接对地（无模块），门关=导通=LOW，判定**完全反相**；
- 若用模块（推挽输出），内部上拉虽不致命，但逻辑仍需按模块极性确认。

**修复**：先上机用万用表/串口打印实测关门/开门电平，再把 `closed` 的判据改成实测值；纯开关方案应改为 `closed = (digitalRead == LOW)`。

### 🔴 高-3｜光电计数无消抖（`photoTask()` 第 245–253 行）

只有边沿检测、没有时间窗，机械抖动或光线抖动会一次通过计成 2–3 人，直接推翻"误计 ≤2%"的验收指标。

**修复**
```cpp
static uint32_t tPhoto = 0;
bool now = (digitalRead(PIN_PHOTO) == LOW);
if (now != photoPrev && millis() - tPhoto > 40) {   // 40ms 去抖窗
  tPhoto = millis(); photoPrev = now;
  if (now) { env.passes++; /* 上报 */ }
}
```

### 🟠 中-4｜触摸是电平触发，按住会反复翻转（第 264–271 行）

按住超过 200 ms 即每 200 ms 翻转一次静音状态，演示时会显得"按键失灵"。**修复**：加 `touchPrev` 边沿判定。

### 🟠 中-5｜`denyBeep()` 阻塞 400 ms（第 197–203 行）

与"无 delay"的设计承诺冲突，且期间不解析串口；还需注意它与 `buzzTask()` 抢同一引脚。可接受，但应在报告中如实说明，或改成状态机。

### 🟡 低-6｜其它

| 位置 | 问题 | 修复 |
|---|---|---|
| L164 | `snprintf(...,"%u", lv)` 传 `uint8_t` 提升为 int | 改 `(unsigned)lv` |
| L190 | `ms>10000 → 3000` 属"替换"而非"钳位"，且 `ms==0` 分支不可达（0 已在 parseCmd 走拒绝） | 改 `ms = min(ms,10000)` |
| 全局 | 无看门狗。Duo 死机时 UNO 本地仍工作（符合设计），但无自恢复 | 可加 `wdt_enable(WDTO_8S)` |
| L322 | `IrReceiver.begin(..., ENABLE_LED_FEEDBACK)` 会占用 **D13 板载 LED**，与 SPI 的 SCK(D13) 无冲突但会造成闪烁 | 改 `DISABLE_LED_FEEDBACK` 更干净 |

## 4 电气与系统可行性（手算）

| 支路 | 电流 | 结论 |
|---|---|---|
| MQ-2 | ~150 mA | |
| 继电器线圈 | ~70 mA | |
| LCD1602 背光 | ~20 mA | |
| OLED | ~20 mA | |
| PCF8591 + 蜂鸣器 + 其它 | ~50 mA | |
| **5V 合计** | **≈ 310 mA** | ✅ 在 USB 500 mA 内 |
| RC522（3.3V） | ~26 mA | ✅ UNO 3.3V LDO 150 mA 内 |
| 舵机（独立 5V） | 待机 100 / 堵转 700–1000 mA | ✅ 必须独立，与设计一致 |
| 风扇（S8050 低边） | 200 mA，Ib=(5−0.7)/1k≈4.3 mA，hFE 120 → Ic 上限 ≈520 mA | ✅ 饱和裕量足够 |

**供电建议**：优先 **USB 5V 供电**；若用 9V 适配器经桶座，UNO 板载线性稳压要耗散 ≈ `(9−5)×0.31 ≈ 1.2 W`，外壳会烫手但不损坏；**不要用 12V**（≈2.2 W，长时间易触热保护）。

### ⚠️ 高风险外部依赖：UNO USB ↔ Duo USB-A

- UNO 的 USB 是 **device** 侧（ATmega16U2 转串口）；Duo 的 USB-A 只有在**内核 host 模式 + 供电**下才能枚举它。
- Milk-V Duo 默认按 device/gadget 工作，IO 底板的 USB-A 是否直连 host 需实测：`dmesg | tail`，插上 UNO 后应出现 `ch341` 或 `cdc_acm`；同时 `ls /dev/ttyUSB*` 出现节点才算成功。
- **若枚举失败**：立即切备用链路——IO 底板四针 `3V3/RX/TX/GND`，`UNO TX(5V) → 1k/2k 分压 → Duo RX`，`UNO RX ← Duo TX(3.3V)` 直连。协议层无需改动。
- 这是全系统**唯一的低置信度项**，验收前必须先打通。

### 电平裕量提醒

RC522 的 MISO 输出 3.3 V 高电平，UNO 的 V<sub>IH</sub> ≈ 0.6×5 = **3.0 V**，裕量仅 0.3 V——理论可用、**临界**。温度/线长一变化就可能误码。建议：加 BSS138 四路转换，或至少把 SPI 降到 4 MHz 以下并缩短杜邦线。

## 6 判定

- **可行性：通过。** 成本、供电、引脚、协议、安全逻辑均成立，唯一硬风险是 Duo 的 USB host。
- **正确性：有条件通过。** 必须修完 §2 的 **高-1、高-2、高-3** 与 §3 的两条 🟠，才可进入验收；其余为改进项。
- **诚实边界：** 未经编译与实际运行验证；本文所有"✅"仅代表静态审查未发现问题，不等同于实机通过。
