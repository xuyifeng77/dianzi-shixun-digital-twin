## 二、B 板是怎么弄起来的（关键事实）

**卡里本来就有系统，没有重烧。** 全新板到手时：

1. 用读卡器看卡：`boot.sd`（3142 KB）+ `fip.bin`（458 KB），时间戳 **2025/5/30 15:27**
2. 与 A 板镜像**同一构建版本** → 判定"已烧录、可直接用"
3. 插卡上电 → 蓝灯闪 → 路由器 DHCP 直接给出 IP

> 📌 经验：**看到卡上有 `boot.sd` + `fip.bin` 就说明是 Milk-V 系统卡**，不用重烧。
> Windows 只能看到那个小的 FAT32 启动分区，系统主体在 ext4 分区里看不见——这是正常的。

## 三、B 板上做了什么（4 条命令）

```sh
cp /etc/network/interfaces /root/interfaces.bak
grep -c "hw ether" /etc/network/interfaces          # 0
echo "pre-up ifconfig eth0 hw ether 02:01:0B:00:00:0B" >> /etc/network/interfaces
echo "milkv-b" > /etc/hostname && hostname milkv-b
sync
reboot
```

与 A 板**唯一的两处不同**：MAC 尾段 `0A`→`0B`，hostname `milkv-a`→`milkv-b`。其余流程完全相同。

## 四、踩到的两个 SSH 坑

### 坑 1 · 新板一开始"抢"了 A 板的 IP

- 现象：路由器里出现"未知设备-9E2B"，MAC `ca:6d:9e:8d:9e:2b`（随机 MAC），IP 却是 `192.168.5.7`
- 原因：新板出厂 MAC 随机，A 板当时未开机，DHCP 把 `.7` 分给了新板
- 处置：改固定 MAC → 重启 → 各归各位（A 板回 `.7`，B 板新拿 `.9`）

### 坑 2 · `REMOTE HOST IDENTIFICATION HAS CHANGED`

- 现象：`ssh root@192.168.5.9` 时报 host key 变更，拒绝连接
- 原因：这个 IP 以前属于别的设备，`known_hosts` 里存着旧指纹
- 处置：`ssh-keygen -R 192.168.5.9`，然后重新连接（输 `yes`）

> 未来每次板子 IP 变化都可能遇到，处理方式固定：`ssh-keygen -R <IP>`。

### ⚠️ 测试过程中的一次真实故障（必须如实记录）

B 板**第一次**测试在 `t_s=1655`（约 27.6 min）时**自动重启**，导致采样中断：

- 现象：SSH 突发 `Connection reset`（是板子重启引起的，不是网络抖动）；重连后 `uptime` 只有 11 min
- 排查：`dmesg` 无 panic / OOM / watchdog 记录；内存全程 139 MB、温度仅 51 ℃ —— **不是资源耗尽**
- 判断：**最可能是持续推理负载下的供电瞬间欠压**（充电头/线材压降）
- 处置：更换供电、重新上电后**完整跑满 60 min 通过**
- 意义：这不是污点，是一条工程结论 —— **边缘节点在持续推理负载下对供电质量敏感**，
  与 `06` 的 P1-7（USB 带载能力需实测）互相印证。答辩时主动讲，比被问出来强。

> 第一次中断的数据文件保留未删（`soak_B.csv`，165 行），作为该现象的原始证据。

### 5.3.2 上行带宽基线（α 架构的成本）

**测量条件**：两块板同时推流（两路 VLC 在线），各自独立测 60 秒。

| 板 | 60 s TX 字节 | 上行带宽 | 换算 |
|---|---|---|---|
| `milkv-a` | 62,338,289 | **1,038,971 B/s** | ≈ 1.04 MB/s ≈ **8.3 Mbps** |
| `milkv-b` | 62,429,032 | **1,040,483 B/s** | ≈ 1.04 MB/s ≈ **8.3 Mbps** |

**测量命令**（同一口径，`/sys/class/net/eth0/statistics/tx_bytes` 差值 ÷ 60）：

```sh
A=$(cat /sys/class/net/eth0/statistics/tx_bytes); sleep 60; \
B=$(cat /sys/class/net/eth0/statistics/tx_bytes); \
echo "TX=$((B-A)) bytes / 60s = $(((B-A)/60)) B/s"
```

**结论**：

> 单节点持续推流（1280×720 H.264 @29.97 fps）占用上行 **约 1.04 MB/s（8.3 Mbps）**，
> 两块板同时在线时各自带宽几乎不变（相差 0.15%），说明瓶颈不在节点侧。
> **这是 α（集中式）架构的带宽成本，也是后面 β（只发结论）的对照基准。**
>
> ⚠️ 口径说明：此数值为**板上 eth0 的发送总量**，包含视频流 + RTSP/TCP 控制开销；
> 与"上行元数据"不是一回事，报告里必须写清是哪一种。
