# 契约冻结与签字规则（一页说清）

> 谁该读：全员。第一次接触"契约/冻结/签字"这三个词的人，读完这页就够用。
> 出处：本节把 [`07-分工与文档责任.md`](07-分工与文档责任.md) §一 铁律 1 与 §四 契约表、[`../A/13-决策记录-有源蜂鸣器与A板IP.md`](../A/13-决策记录-有源蜂鸣器与A板IP.md) §八 签字页讲成人话。

---

## 一、三个词分别指什么

| 词 | 一句话 | 不是这个意思 |
|---|---|---|
| **契约** | 两个岗位**交接口**的书面约定：谁产出、谁消费、字段叫什么、单位是什么、多久一次、失败怎么办 | 不是设计文档，不写内部算法；也不是需求，不讲"为什么做这个项目" |
| **冻结** | 给契约**钉一个版本号**（如"契约 1 v1.0，D2 冻结"），从此**改动必须走签字流程**，不能谁想改就改 | 不是"不许改"，是"改要留痕、要通知用方" |
| **签字** | 责任人在签字页写下**岗 / 确认内容 / 签字 / 日期**，等于承诺"我这一侧按这个版本实现，不再单方面动" | 不是评优盖章，不是走过场，也不是"我同意你说的都对" |

一句话：**契约是接口的宪法，冻结是生效，签字是宣誓。**

---

## 二、冻结的到底是什么（三个面）

只冻这三样，别的一概不冻：

1. **名字**——字段名、列名、端口名、节点名。`buzzer_level` 就是 `buzzer_level`，不能有人写 `buzzer_grade`、有人写 `alarm`。
2. **量纲**——单位与格式。毫秒还是秒、`NA` 还是空、`192.168.5.9` 还是 `192.168.5.09`。
3. **边界**——谁产生、谁消费、频率、超时、失败行为（断线报什么、丢帧记在哪）。

**不冻**：内部算法、代码结构、变量命名、界面长什么样、你用什么库实现。

---

## 三、为什么非冻不可（本仓库的真实教训）

- 仓库里一度**同时存在三套协议**：`02 §4.2` 的二进制帧、`03 §7` 的扩展报文类型、已实现的 ASCII `@` 帧。四个人各按各的理解写，**第 3 天必然对不上**，只能返工。这正是 [`07 §一`](07-分工与文档责任.md) 铁律 1 的由来。
- 串口设备名一处写错就全组踩坑：CH340 克隆板是 `/dev/ttyUSB0`，16U2 原装板是 `/dev/ttyACM0`，**同一份代码在两块板上跑不一样**（见 [`../A/06-项目审查报告.md`](../A/06-项目审查报告.md) P0-5）。
- 蜂鸣器从"无源 + 频率"改成"有源 + 等级"以后，如果 CSV 还留着 `freq_hz`，D 的数据和 C 的固件就永远对不上。所以 schema v1.1 直接**明令禁止** `freq_hz`/`tone`，只认 `buzzer_level` + `pattern_ms`（[`../D/契约3-实验数据CSV-schema-v1.1.md`](../D/契约3-实验数据CSV-schema-v1.1.md) §6）。

**共同点**：这些都不是"写得不好"，是**接口没钉死，两侧各自演进**。契约冻结就是把这件事的成本压在一次会议上，而不是压在答辩前两天。

## 五、签字页长什么样（照抄即可）

```markdown
## 签字（冻结生效）

| 岗 | 确认内容 | 签字 | 日期 |
|---|---|---|---|
| A | 契约 1 采用 ASCII `@` 帧（v1.1），`02 §4.2` 二进制帧标为"设计预案，未采用" | ____ | 11-__ |
| B | 按 v1.0 实现桥接解析，端口自动探测 `ttyUSB0`/`ttyACM0` | ____ | 11-__ |
| C | 按 v1.0 输出七种行，`@Q` 必须回一行 | ____ | 11-__ |
| D | 数据列名与契约 1 字段逐字一致 | ____ | 11-__ |

> 未签字 = 仍可改；签字后改动需 A 重新签字，并同步 02/07/09/10 四份文件。
```

签字只需要四列：**谁的岗、确认了哪一句技术内容、签名、日期**。确认内容要写成"可验证的句子"（"按 v1.0 输出七种行"），不能写"同意"两个字——三个月后没人知道当时同意了什么。

## 六、冻结之后要改，怎么办（5 步，30 分钟内能走完）

1. **谁提**：任何发现自己这侧必须变的岗位都能提，**但只在群里提不算数**。
2. **写清三件事**：改哪一条、为什么非改不可、影响谁（用方是谁、已写了多少代码要跟着改）。
3. **A 判**：改动是否破坏已实现方？是否只是"换个写法"？小改动升小版本（v1.0 → v1.1），大改动才允许重写。
4. **签字 + 升版本号**：旧版本**不删**，加一行修订记录（改了①②③），让人能查到"什么时候因为什么变的"。
5. **同步 + 宣布**：按影响清单改文件（通常是契约本身 + 记录表 + 代码 + 相关 README 四五处），然后在群里贴"契约 X → vY，影响 A/B/C/D 哪几条"。

## 七、五个常见误用（踩了必返工）

| 误用 | 后果 | 正确做法 |
|---|---|---|
| 冻结前不读代码，照着文档签字 | 签的版本和代码不一致，第一天就冲突 | 冻结前跑一次真实链路，用**实际输出**核对字段 |
| 冻结后口头改，"反正大家都知道" | 三天后没人记得改了什么，新人按旧版写 | 走 §六 五步，哪怕只改一个字段名 |
| 把契约写成设计文档 | 谁都不看，等于没冻 | 只留"字段 / 单位 / 频率 / 失败行为"四类内容 |
| 一个人代四个人签 | 出事没人认，答辩一问就露 | 每人自己签，签"我这一侧怎么实现" |
| 拿聊天记录当契约 | 搜不到、翻不回、没法 diff | 只认仓库里的文件 + 签字页 |

## 八、和 git 的关系（我们的留痕方式）

- 契约文件的每次实质修改都**单独提交**，commit message 写"契约 X → vY：改了什么、影响谁"。
- 旧版本不删；需要对照就用 `git log -- <文件>` 看演变。
- **签字页随决策记录一起提交**，签字日期与 commit 时间对得上，就是这套流程被执行的证据。
